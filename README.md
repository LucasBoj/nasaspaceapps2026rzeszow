# SELENE OPS — lunar south pole landing-window planner

Entry for the **NASA Space Apps Challenge 2026** (local event Rzeszów), challenge *Lunar Landing Site Navigator / CLPS Lunar Mission Browser*.

**Live:** https://selene.byst.re/

Pick a site near the lunar south pole, a lander and a date window. SELENE OPS simulates sunlight, Earth visibility and battery charge hour by hour and answers *feasible / not feasible*, with the best landing window. Any point in 80–90°S can also be analysed in the browser.

## Data

| What | Source |
|---|---|
| Terrain | NASA LRO LOLA `ldem_75s_120m_float` (PDS Geosciences Node); 240 m and 60 m variants for custom points and validation |
| Landing sites | Wueller et al. (2026), JGR Planets, doi:10.1029/2025JE009434, Table A1 via Zenodo doi:10.5281/zenodo.17084058 (CC-BY-4.0) |
| Sun and Earth positions | JPL DE421 and NAIF lunar orientation kernels, computed with Skyfield |
| Imagery | NASA/JPL Moon Trek, LRO WAC mosaic |
| Validation | JPL Horizons; NASA LOLA illumination maps (Mazarico et al. 2011) |

The app is not affiliated with or endorsed by NASA.

## Use of AI (Super Intelligence)

We follow the Space Apps rule on the use of AI. In short: **AI helped us write the code and made the 3D lander models; it did not produce any scientific number.**

**What AI was used for**

- **Code, debugging, tests and documentation** — Claude Code (Anthropic, Claude Opus 5.5) wrote and reviewed most of the frontend (Blazor WebAssembly, CesiumJS), the Python data pipeline, the unit tests (xUnit, pytest), the browser tests (Playwright) and the documentation, under the team's direction. Every session is listed with its date in [`docs/AI_USAGE.md`](docs/AI_USAGE.md). The first app skeleton (commits `323edd4`, `a2f267d`) was made with Claude Code (Anthropic) in the IDE, from a prompt drafted with Claude (claude.ai).
- **3D lander models** — the five lander models are AI-generated: a concept image from **Meshy AI**, turned into 3D by **Microsoft TRELLIS.2** (MIT), then optimised with glTF Transform and meshoptimizer ([`tools/optimize-models`](tools/optimize-models)). They are stylised visualisations, not manufacturer CAD. Logos, flags and insignia that the AI put on the textures are painted out (`tools/optimize-models/redactions.json`).
- **Concept images** for those models (Meshy AI).

**What was not generated by AI**

- **All scientific data.** Sunlight, Earth visibility, horizons and the battery simulation come from NASA LRO LOLA terrain and JPL DE421 / NAIF ephemerides, computed deterministically by our code. The same inputs always give the same output.
- **Lander specifications** come from published sources (FCC filings, manufacturer pages, NASA documents). Every number has a source link, or is marked as an assumption or as derived.

**How we checked the results**

- Sun and Earth directions match **JPL Horizons** to ≤ 0.005° (`pipeline/validate_horizons.py`, offline snapshots in `pipeline/data/horizons/`).
- Sunlit time matches the **NASA LOLA illumination maps** when compared like for like, at their own pixel centres and on the same DEM (`pipeline/compare_nasa_pixels.py`, `pipeline/compare_nasa_illumination.py`).
- The in-browser analysis of custom points matches the pipeline for the 9 regions within ~2 percentage points.
- Over 100 unit tests and browser tests in Chromium, Firefox and WebKit run before each deploy.

**Where it is disclosed**

- In the app, a visible “AI-generated 3D model” badge appears whenever a lander model is on screen. The Credits dialog names every tool.
- `index.html` carries `<meta name="ai-assistance">`. Each GLB names the AI tools in `asset.generator` and `asset.extras`. `landers.json` has `aiGenerated` for every model.
- Every data file from the pipeline carries a `provenance` note: the code was written with AI assistance, and the values come from NASA/JPL data.
- Screenshots and the link preview image that show a lander say “Contains AI-generated 3D models”.
